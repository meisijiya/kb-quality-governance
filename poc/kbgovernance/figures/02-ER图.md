## 主要关系的基数与可选性说明

下表逐条说明 E-R 图中各关系的基数符号含义与业务上的可选性，可直接改写为论文正文的一段文字。

| 关系 | Mermaid 记号 | 基数含义 | 可选性说明 |
| --- | --- | --- | --- |
| document → ticket | `\|\|--o{` | 一篇文档可被 0..N 条工单关联 | ticket.linked_doc_id 允许为空，表示该工单尚无对应文档 |
| document → stale_document | `\|\|--o{` | 一篇文档可被判定为 0..N 次腐化（每次检测产生一条记录） | 风险分数累计到 3 才写入，判定理由随记录留存 |
| document → duplicate_group | `\|\|--o{` | 一个重复组包含 1 主文档 + N 从属文档 | primary_doc_id 必选且必须是组内某一篇；组内相似度需超过阈值 |
| cluster_result → knowledge_gap | `\|\|--o{` | 一个聚类簇可派生 0..N 条缺口记录 | 仅当覆盖度中位数低于阈值时才落 knowledge_gap 行 |
| cluster_result（成员关系） | 不建外键表 | 簇内工单数记于 knowledge_gap.ticket_count | 代表工单记于 representative_ticket / representative_text，缺口判定证据即在此处 |
| ticket（意图标签） | 非外键 | 工单意图由业务侧给定并参与簇内多数投票 | 聚类得到的簇与原有意图标签是两套标签，后者用于工单侧统计 |

**图注建议**：图 4-1 给出系统数据库的实体关系设计。核心线索是「一条链路贯穿三类治理对象」：ticket 经 linked_doc_id 关联 document，工单向量聚类结果落 cluster_result 并在覆盖度不足时派生 knowledge_gap；document 一侧派生 stale_document 与 duplicate_group。工单与文档都是只读输入，治理结论由算法层产出后统一落库，不设用户与审计实体，日期时间统一以 ISO-8601 文本存入 TEXT 列。

## 表清单速查

6 张表即系统的全部持久化对象。

| # | 表名 | 中文名 | 说明 |
| --- | --- | --- | --- |
| 1 | document | 文档表 | 300 篇知识文档，含生效日期、最后修改时间与状态 |
| 2 | ticket | 工单表 | 2000 条工单原文、意图标签与紧急程度 |
| 3 | cluster_result | 聚类结果表 | HDBSCAN 簇、粒度、最小簇规模与使用阈值 |
| 4 | knowledge_gap | 知识缺口表 | 覆盖度不足的意图簇，含代表工单与补录优先级 |
| 5 | stale_document | 腐化文档表 | 规则命中的过期文档、风险分数与判定理由 |
| 6 | duplicate_group | 冗余组表 | 高相似文档分组，含主文档与组内最大相似度 |
