# 人工标注规程（企业知识库质量治理 · 标注材料）

> 适用范围：`poc/kbgovernance/annotation/worklist_A.csv`（A 卷，全部条目）与
> `poc/kbgovernance/annotation/worklist_B.csv`（B 卷，100 条重叠子集）。
> 配套生成器：`poc/kbgovernance/annotation/make_worklist.py`（固定随机种子 42，可重复生成同一份工作单）。
>
> 本规程按**现行口径**写：内容腐化拆成「内容过期」「维护周期」两个独立口径，各自独立判定、各自报 P/R/F1；
> 缺口判定的单元是**业务意图**（不是意图簇），标注对象是**全部 30 个业务意图**。
> 第五、六节是给项目方看的（评分口径与限制），**标注者作答时不必读**。

---

## 一、总体规则

1. **一次只判一条**。按 `item_id` 顺序逐条处理，不要跳着填、不要先看结果再回头改判据。
2. **按问句作答**。每条都有一句 `judge_question`，先读问句，再读 `material`，按问句要求作答。
3. **判定依据只能是工作单里给出的材料**。不查外部资料、不上网、不问同事、不参考自己以前对同类条目的印象。
4. **拿不准就选「无法判断」，并在 `reason` 里写清缺什么信息**。「无法判断」是合法答案，不是失败；但「无法判断」必须给出理由，不能空着。
5. **不要修改除判定列以外的内容**：`item_id` / `category` / `source_ref` / `judge_question` / `material` 一律保持原样（表格被截断、串行、字段错位时原样发回，不要修补）。
6. **两位标注者独立完成**。A 卷与 B 卷中有 100 条是同一条目（材料逐字相同），但**判定结果各自独立填写，互相不可见对方答案**；请勿与另一位标注者讨论具体条目的结论。
7. **判定值照抄合法取值**。不要自造词、不要加解释到判定列里（解释写 `reason` 列）。
8. **腐化类的两个问题各答各的**。同一条腐化条目有两个独立问题（内容过期口径 / 维护周期口径），
   答在两列里，**不要因为第一个问题的结论去推断第二个**，也不要把一个问题的理由写进另一个问题。

## 二、五类条目各自的判定标准与合法取值

### 2.1 文档内容合理性（`item_id` 形如 `DOC-001`）

**问的是什么**：这篇文档的正文是否语义通顺？系统给出的领域归属 `category` 是否正确？

**判「不合理」的典型情形**（至少命中一条）：

- 正文有断句错误、缺字、语句自相矛盾、同一句里前后语义打架；
- 正文与标题对不上（标题讲的是 A，正文写的是 B）；
- 正文内容与所属 `category` 明显不符（例如「财务管理」类别下写的是人事流程）；
- 正文是空壳、重复堆砌、与业务无关的套话，导致无法读出它到底规定了什么。

**判「合理」**：正文语义通顺、能读出明确的业务规定，且 `category` 与正文内容相符。

**合法取值**：`合理` / `不合理` / `无法判断`（填在 `decision` 列）

---

### 2.2 工单内容合理性（`item_id` 形如 `TKT-001`）

**问的是什么**：这条工单的表述是否像真实员工提问？系统给出的意图标签 `intent_label` 是否与工单的真实诉求一致？

**判「不合理」的典型情形**：

- 表述不像人写的（语句截断、前后重复、空洞到没有具体诉求，例如只有「咨询一下」这类无信息量的话）；
- 工单正文与意图标签指向两件事（例如正文问的是「密码过期能不能延期」，标签却写「门禁权限申请」）；
- 正文里夹带了与诉求无关的大段内容。

**判「合理」**：表述自然、有具体诉求，且意图标签与诉求一致。

**合法取值**：`合理` / `不合理` / `无法判断`（填在 `decision` 列）

---

### 2.3 缺口清单（`item_id` 形如 `GAP-001`）

**问的是什么**：这个**业务意图**下提出的问题，知识库里有没有对应条目支撑？

**判定单元 = 业务意图**：一条工作单对应一个业务意图（不是意图簇）。
本轮把**全部 30 个业务意图**都做成了条目（理由见 6.2），所以 `GAP-001`～`GAP-030` 各自是一个不同的业务意图。

**材料里的关键字段**

| 字段 | 含义 |
| --- | --- |
| `该意图工单总数` | 该业务意图下的工单条数（各意图簇条数之和） |
| `参与聚合的意图簇数` | 该意图被聚成几簇（3 簇或 8 簇） |
| `意图级覆盖度` | 该意图各簇覆盖度的**最小值**（min 聚合） |
| `意图簇明细` | 每簇的簇号、簇内工单数、簇覆盖度、代表工单及其覆盖度 |
| `代表工单原文` | 取自三个不同意图簇（覆盖度低 / 中 / 高各一条）的工单原文 |
| `知识库候选文档` | 从全库 300 篇里按与本意图工单的语义接近度取的前 3 篇，含标题与正文分段 |

**判定标准**

1. 覆盖度数值只说明「系统拿现有文档去匹配这些工单时匹配上的比例高不高」，**不等于**「这个意图真的没有文档能支撑」。
2. 请**结合代表工单原文与候选文档的正文**判断：这条工单提出的诉求，按常理该由一篇什么样的文档来支撑？候选文档里有没有讲同一件事的段落？
3. 若你认为**该意图其实已有文档能支撑，只是覆盖度数值偏低**，判 `不是真缺口`，并在 `reason` 里写明是哪一篇文档的哪个段落支撑了该诉求（例如「诉求是差旅住宿标准，候选文档第 3 段讲了同一件事」）。
4. 若候选文档明显都在讲别的事、或代表工单原文过于笼统，导致你无法判断，判 `无法判断`，并写明「需要看该意图下的其它工单 / 需要看该意图下全部文档」之类缺什么。

**合法取值**：`是真缺口` / `不是真缺口` / `无法判断`（填在 `decision` 列）

---

### 2.4 腐化清单（`item_id` 形如 `COR-001`）

**问的是什么**：本条要你回答**两个互不影响**的问题：

- ①**内容过期口径**：这篇文档的**正文内容本身**是否已经过期（正文写明的时间口径已经是过去，不能再作为当前依据）？
- ②**维护周期口径**：这篇文档是否**长期无人维护，且同域已有更新版本**？

两个问题**各填一列**：`decision_content_expiry` 与 `decision_maintenance`。

**材料里的关键字段**：`文档编号`、`标题`、`领域归属 category`、`本文所属业务意图`、`最后修改日期 last_modified`、
`语料基准日`（知识库语料的统一起算日 = 2026-10-01）、`同域同主题文档清单`、`正文`。

> `同域同主题文档清单` 是**中性事实**：它列出「同一领域、同一业务意图」下每篇文档的编号、最后修改日期、标题（本文带 `← 本文` 标记），
> 只陈述「有哪些文档、各自什么时候改过」，**不代表任何判定**。清单里的条数多、日期新，说明该主题有人维护；清单里没有更晚的文档，说明没有更新版。

#### ① 内容过期口径（填 `decision_content_expiry`）

**判据**：**只看正文**。正文里写明的时间口径（生效日期、有效期截止日、适用年度、所废止的旧版本等），
相对语料基准日 **2026-10-01** 是否**已经是过去**，以至于正文写明的内容已经不能作为当前依据？

- 判 `正文已过期`：**必须**在 `reason` 里引用正文原文片段、指出具体位置。
  例：正文末句写「该方案有效期至2025年6月30日，延期须另行报批」，该有效期早于基准日 → 判 `正文已过期`。
- 判 `正文未过期`：正文里没有任何时间口径（纯流程性说明），或时间口径仍在基准日之后。
- 判 `无法判断`：正文的时间口径表述本身有歧义（例如只写「近年」不写具体年份），在 `reason` 里写清缺什么信息。

**合法取值**：`正文已过期` / `正文未过期` / `无法判断`

#### ② 维护周期口径（填 `decision_maintenance`）

**判据**：本文是否**同时**满足下面两个条件？

- **（a）长期无人维护**：最后修改日期距语料基准日 2026-10-01 超过 18 个月，即最后修改日期**早于 2025-04-01**；
- **（b）同域已有更新版本**：在 `同域同主题文档清单` 里，存在**最后修改日期比本文更晚**的其它文档（说明同一主题已经更新过，本文停留在了旧版本）。

**两个条件都满足**才判 `维护状态已失控`。
**只有（a）没有（b）**（很久没更新，但同域没有更新版）→ 判 `维护状态正常`。
**只有（b）没有（a）**（同域有更新版，但本文本身改得不算久）→ 判 `维护状态正常`。

**合法取值**：`维护状态已失控` / `维护状态正常` / `无法判断`

#### 两个问题的分工（重要）

- ① **只依据正文**，不要拿同域文档清单当依据；正文没写过时的内容，即使同域有新版，也不算「内容过期」。
- ② **只依据最后修改日期与同域文档清单**，不要拿正文里的时间口径当依据；正文里写了旧日期，但它最近刚被改过，也不算「维护失控」。
- ② 判 `维护状态已失控` 时，**不必**引用正文片段（正文片段只在 ① 里需要）；① 判 `正文已过期` 时，也**不必**引用同域文档清单。
- 任何一列判 `无法判断`，都在 `reason` 里写明缺什么信息（可以分两行写，分别对应两个问题）。

### 2.5 重复清单（`item_id` 形如 `DUP-001`）

**问的是什么**：这一组里的文档讲的是不是**同一件事**？

**材料里的关键字段**：`重复组号 group`、`组内文档数 size`、`组内成员文档编号 member_docs`、
`组内最大余弦相似度 max_sim`，以及**每个成员的标题与正文全文**。

**判定标准**

1. `max_sim` 是向量相似度，只是参考线索。判断以标题与正文为准：同一篇文档换了几个措辞、调了句序，但规定的是同一件事 → 算同一件事；只是**主题相近**（例如同属「差旅费报销」但一条讲报销范围、一条讲报销材料）→ 不算同一件事。
2. 判 `不是真重复组` 时，在 `reason` 里写清哪两篇只是主题相近、并非同一件事。

**合法取值**：`是真重复组` / `不是真重复组` / `无法判断`（填在 `decision` 列）

## 三、盲化：工作单里有什么、没有什么

本轮工作单对**系统判定**做了盲化处理，请照此理解你看到的东西。

**工作单里没有**（一个也没有）：

- 任何系统命中了哪些规则、规则分数、风险分、系统的判定说明；
- 任何「这篇文档是不是缺陷 / 是不是真缺口 / 是不是真重复组」的参考答案或答案标记；
- 任何「这条样本是刻意埋设的对照 / 是重复件继承」之类的标记。

**工作单里有**（都是可读材料）：

- 标题、领域归属、所属业务意图、正文全文、创建/最后修改/生效日期、状态、被引用次数；
- 工单的渠道、时间、紧急程度、状态、意图标签、正文；
- 意图级的工单数、簇数、覆盖度、代表工单原文、候选文档正文片段；
- 重复组的组号、成员编号、成员标题与正文、组内最大余弦相似度；
- 腐化条目的「同域同主题文档清单」——**这是中性事实**（有哪些文档、各自什么时候改过），不是系统判定，也不代表「本文已过时」。

**换句话说**：材料里出现的**数字与事实**都可以直接看、直接复核；材料里出现的**结论**一个都没有。
判据是公开的（写在第二节和每条的 `judge_question` 里），但每一条的判定结果要你自己下。

## 四、填写方式与回收

**要填的列**（其余列一律不动）：

| 列 | 怎么填 |
| --- | --- |
| `decision` | 单标签类（文档 / 工单 / 缺口 / 重复）填第二节里该类的合法取值之一，逐字一致 |
| `decision_content_expiry` | **仅腐化清单**：填 `正文已过期` / `正文未过期` / `无法判断` |
| `decision_maintenance` | **仅腐化清单**：填 `维护状态已失控` / `维护状态正常` / `无法判断` |
| `reason` | 一句话说清依据。引用原文片段时用中文引号包住；判 `无法判断` 时写清缺什么信息 |
| `annotator` | 你的代号（如 `A1`、`B1`） |
| `annotated_at` | 填写时间，格式 `YYYY-MM-DD HH:MM`（24 小时制） |

**操作注意**

- 直接在 Excel 里打开编辑即可（文件是 UTF-8 with BOM，中文不乱码）。
- `material` 里带换行是正常的，**不要删除换行**，也不要合并单元格。
- 不要改列顺序、不要插入或删除列、不要重排行序。
- 腐化类条目**两个判定列都要填**，不要只填一个；单标签类条目的两个判定列**留空**。
- 填完**另存为**新文件，不要覆盖原文件：
  - `poc/kbgovernance/annotation/worklist_A_filled.csv`
  - `poc/kbgovernance/annotation/worklist_B_filled.csv`
  - 编码同样选「UTF-8（带 BOM）」，CSV UTF-8。
- 原 `worklist_A.csv` / `worklist_B.csv` 保持原样，它们是**可复算的基线**（同一份输入重复生成，逐字节一致）。

**交回之后做什么**

把两份 `_filled.csv` 交回项目方，由项目方运行评分脚本：

```bash
python poc/kbgovernance/annotation/make_worklist.py \
  --score \
  --a poc/kbgovernance/annotation/worklist_A_filled.csv \
  --b poc/kbgovernance/annotation/worklist_B_filled.csv
```

脚本会输出：两卷的分类计数与重叠条目数、两位标注者的**逐条一致率**与 **Cohen's Kappa**（腐化类按两个标签分别算）、
缺口类的**意图级** P/R/F1、腐化类**两个口径各自**的 P/R/F1 与人工标签对系统标签的一致率、
「系统判过但参考真值不成立」条目的**分层报告**（逐条列出人工标签与误报归因），以及重复清单的对照。

参考真值是在评分时由脚本从仓库判定产物现场推导的，**从未写进工作单**，所以交回前不需要、也不应该去找答案。

## 六、条目数量实况

### 6.1 两卷的条目分布

| 类别 | A 卷条目 | B 卷条目（重叠子集） | 抽样来源与规模 |
| --- | ---: | ---: | --- |
| 文档内容合理性 | 30 | 15 | `docs.csv` 300 篇中按 `doc_id` 升序随机抽 30 |
| 工单内容合理性 | 200 | 15 | `tickets.csv` 2000 条中按工单编号升序随机抽 200 |
| 缺口清单 | 30 | 30 | `gap_clusters_best.csv` 95 行聚合出的 **30 个业务意图全量**（见 6.2） |
| 腐化清单 | 20 | 20 | `corrupt_docs.csv` 300 行里系统已给出判定的 69 行，按四象限分层抽 20（见 6.3） |
| 重复清单 | 20 | 20 | `dup_groups_best.csv` 22 组里按组号升序随机抽 20 |
| **合计** | **300** | **100** | |

- **B 卷选样规则**：优先覆盖全部缺陷清单条目（缺口 30 + 腐化 20 + 重复 20 = 70 条），
  再补内容合理性条目（文档类 15 条 + 工单类 15 条），合计 100 条。
- B 卷这 100 条的 `judge_question` 与 `material` 与 A 卷**逐字相同**，判定列各自留空、互不可见。
- 工单抽样比例是 2000 条的 10%（200 条），本轮按预算取满。

### 6.2 缺口清单为什么是 30 条全量

缺口判定的单元是**业务意图**，不是意图簇：

- `gap_clusters_best.csv` 共 95 行（全部意图簇），聚合出 **30 个业务意图**；
- 意图级覆盖度按「各簇覆盖度取最小值」聚合，分母就是意图；
- 要算意图级的 P/R/F1，就必须覆盖**全部 30 个意图**，抽 15 条会让分母失真。

因此本轮把 30 个业务意图**全量**做成条目，一条不多一条不少（`GAP-001`～`GAP-030`）。
`gap_intents_best.csv`（5 行）是系统按覆盖度阈值选出的缺口清单，本轮**只用于交叉核对意图级数值**，
不作为标注对象的范围。

### 6.3 腐化清单的四象限分层

分层依据是系统对**两个口径各自**的规则加权分（≥3 分即视为该口径命中），抽样在分层内随机进行：

| 分层 | 候选池（篇） | 本轮抽样（篇） |
| --- | ---: | ---: |
| 内容过期 × 维护周期（双命中） | 1 | 1 |
| 只命中内容过期 | 31 | 9 |
| 只命中维护周期 | 37 | 10 |
| 两口径均未命中但被系统判过 | 0 | 0 |
| **合计（系统已给出判定的行）** | **69** | **20** |

- 第四象限实际为空：本语料里凡是被系统判过的行（`risk_score` ≥ 3），至少命中一个口径。
- 其余 231 行系统根本没给出腐化判定，没有「系统说法」可复核，不进本轮样本。

- 所有抽样共用随机种子 42，候选集合先按主键升序排序再抽，**重跑脚本产出逐字节一致**。

## 七、本次标注的已知限制（如实列出）

1. **本轮不是严格盲测**。语料是本项目自造的合成语料（生成器 `poc/kbgovernance/gen_data.py` 在仓库内可见），
   标注者若读过生成规则，可能推断出部分条目的答案。工作单本身不含任何参考真值列、也不落盘答案表，
   但**语料来源本身不是黑盒**，这一轮的一致性数据因此不能当作严格盲测证据。
2. **内容过期口径的参考真值与系统规则同源，属循环验证**。系统规则是照着生成器的埋设模板写的
   （埋设的过期句型固定为「有效期至…」「自…起施行…同时废止」「截止…」「依据…年度制度制定，现已失效」等），
   因此该口径的满分（内容过期 P/R/F1 均为 1.0000）**不能当作独立评测结果**，只能说明规则在自己造的数据上自洽。
3. **维护周期口径的 7 篇系统误报里，6 篇是生成器刻意埋设的「4% 自然陈旧但不算缺陷」对照集样本，
   1 篇（DOC0242）继承了主文档 DOC0241 的陈旧 `last_modified`**。这 7 篇误报**只属于维护周期口径**，
   内容过期口径 0 篇误报。含义：该口径的规则会把「本来就旧、但有更新版覆盖」的文档一起捞进来，属于规则过召。
4. **两类内容合理性条目没有独立的参考真值**。「文档内容合理性」「工单内容合理性」判的是语料本身是否通顺、标签是否贴切，
   仓库里没有针对这两类的人工金标；评分时只能给出两位标注者之间的一致性，给不出对真值的指标。
5. **判据是公开的，标注结果会与系统高度一致**。工作单把判据写明，因此人工标签与系统标签的一致率应当很高；
   人工标签对**埋设真值**的 F1 若低于系统读数，说明的是「规则过召」而不是标注错误
   ——按公开判据，那 7 篇对照集/重复件本来就该被判成「维护状态已失控」。
6. **一致性证据的表述方式由后续决策确定**。是写「标注者间一致率」，还是写「对参考真值的一致率」，本规程不预设口径；
   本轮只保证原始判定可追溯、可复算。
