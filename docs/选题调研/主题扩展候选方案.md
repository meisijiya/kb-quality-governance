## 1. 扩展思路说明

已有 11 个主题把「**检索**」「**预测**」「**排课约束**」「**知识治理**」四条主线占满了。要跳出这个范围，靠的不是继续找新场景，而是**找新的问题结构**。本文从四个维度扩展：

### 维度一：从已有场景横向迁移 —— 把「知识治理」这个任务模式搬走

《企业级知识库选题方案.md》的核心洞察是：**任何「文档 / 日志 / 工单 / 配置」类数据，都同时存在三种腐化形态**：

- **缺口**：用户反复问、但系统里根本没有对应内容
- **腐化**：内容还在，但已过期/失效/与现状不符
- **冗余**：同一件事有 N 份说法，还互相矛盾

这三个「形态学」是与场景无关的。把它搬到日志上 → **缺口=未被任何模板覆盖的异常模式，腐化=日志模板失效，冗余=告警重复轰炸**；搬到 issue 上 → **缺口=没人问过的新问题，冗余=同一个问题被问了 50 次**。所以维度一的 3 个方案不是「新场景」，是**同一套方法论的三次验证**，这本身就是论文里可以写的对比实验。

### 维度二：企业级 IT 与运维 —— 主攻运维岗，这是你的优势区

往届 14 个题目里，**0 个是运维/IT 方向的**。运维类毕设天然适合做测试用例表（接口清晰、输入输出确定、异常路径明确），正好匹配你投测试开发/运维岗的简历。这个维度筛掉了一切需要联网爬虫、需要真实企业账号、或算法含量低于「规则引擎」的题目，只留下三种数据结构：

1. **有明确标签的历史事件流**（发布记录 → 变更风险）
2. **天然是图的关系结构**（权限授予关系 → SoD 冲突）
3. **有公认最优解的在线策略**（缓存替换 → Belady/ARC）

### 维度三：图 / 网络 —— 图算法含量高、好讲、NetworkX 全家桶兜底

图方向的独特优势：**算法正确性可以「看一眼图就知道」**，这正好命中《校园场景选题方案.md》提出的 vibecoding 核心判据（「bug 出现时能否 10 分钟定位」）。画出来 conflicted 的两个节点高亮，bug 无处遁形。本维度重点找**有免费公开 API 拿真实数据**的图（OSV 漏洞库、ecosyste.ms 依赖图、OpenAlex 引用网络），避免自造。

### 维度四：优化 / 运筹 —— 与「排课」同族，但数据更小、解更成熟

排课已经被占用（⑦），但 OR-Tools CP-SAT 官方示例库里还躺着 **bin packing / job shop / employee scheduling** 三个官方样例 —— 这些是「照着改数据模型」级别的难度，比排课的软约束权重更简单，2 天能跑通。`scipy.optimize.linear_sum_assignment`（匈牙利算法）是二次分配的标准实现，`scipy.optimize.milp` 与 `pulp` 覆盖线性/混合整数规划。这三个库的 GitHub 星数与最后提交时间已核实（见下），**都是 Google / SciPy / COIN-OR 维护的官方件，不是冷门技术**。

### 本文的统一淘汰标准

以下情况直接剔除，不写进方案：

- 需要 7B+ 模型 → 硬件不允许
- 需要 CUDA 训练大模型 / 需要调参才能收敛 → vibecoding 不可控
- 数据必须联网爬取且无稳定 API → 会卡住
- 往届撞车概率 > 40% 且无强差异化 → 查重风险
- 算法含量低于「一个可评估的模型 + 一个可消融的改进」→ 老师红线

**关键选型理由**：BGL 与 Thunderbird 的日志**第一列 `-` 表示非告警、其他表示告警**，这是论文原文明确写的 —— 也就是说「告警 vs 非告警」是**天然免费的人工标注**，直接给出 F1 指标，不用你手工标注。这在本科毕设里是稀缺资源。

**规模控制（vibecoding 关键）**：**不要跑 Thunderbird（2.1 亿行）**。只跑 BGL 抽样的 200 万行 + HDFS_v1 抽样的 100 万行。实测 Drain 在这两个数据集上都是分钟级。列数不是表结构意义上的「列」，日志的「列」= 解析出的事件模板 ID，几十到几百个，远低于 30 列红线。

- 获取方式：`https://github.com/logpai/loghub` 直接下载原始 zip，或 `https://zenodo.org/records/8275861`（Loghub-2.0，ISSTA'24 版）
- **Loghub-2.0 仓库实测数据**：GitHub API 查得 **153★，最后提交 2025-10-08**，仍在维护。原始 loghub 仓库下载量已超 9 万次 / 450+ 机构（论文原文）

**轨道 B（自造工程侧数据，用于系统演示）**：自造 5000 条「服务 × 告警规则 × 时间窗」的监控告警流（字段：告警ID、来源服务、规则名、触发时间、级别、标签、处理状态、关联工单）。这一轨只用来跑通系统界面，不作为算法评估数据。

**评委问「数据是真是假怎么答」**：
> 「算法评估用的是 Loghub 公开数据集，BGL 和 Thunderbird 是真实的超算生产日志，**告警标签是数据集自带的人工标注**，不是我造的。我自己另外造了 5000 条监控告警流，这部分在论文第 3.2 节写明了构造规则（服务拓扑 × 告警规则集 × 时间衰减），并且只用于系统功能演示，不参与算法指标计算。」

### 5. 系统模块清单（7 个）

1. **日志接入与解析模块**：上传/路径读取 → Drain 模板抽取 → 事件表入库（百万行级别）
2. **告警流水模块**：告警记录的录入、标签、状态流转
3. **模板挖掘与事件浏览模块**：模板列表、模板样例、模板命中趋势
4. **告警归并模块**：HDBSCAN 聚类 → 告警风暴簇 → 每簇代表告警
5. **根因线索定位模块**：按服务调用链拓扑，给出「最可能的源头服务」候选（用告警时间领先性 + 拓扑距离打分）
6. **抑制策略配置与模拟**：燃烧率阈值配置 → 历史数据回放 → 对比抑制前后告警条数
7. **治理看板与报告**：告警收敛率趋势、TOP 风暴簇、SLA 达成率、一键导出周报

**数据库设计（9 张表）**：`log_file` 日志文件、`event_template` 事件模板、`event` 解析事件、`alert_rule` 告警规则、`alert` 告警、`alert_cluster` 归并簇、`service` 服务、`topology_edge` 依赖边、`suppress_policy` 抑制策略配置 + `user`。
ER 图素材：服务拓扑自关联多对多、告警→模板多对一、归并簇→告警一对多 —— 内容充足。

### 8. vibecoding 友好度：**5 / 5**

理由：
- 数据规模可控（抽样 200 万行，非 59 万 × 460 列那种内存炸弹）
- **零调参**：Drain 与 HDBSCAN 都是无参构造，这是本文 13 个方案里调参负担最小的

## 1-B 基于语义聚类的开源项目重复提问识别与 FAQ 自动沉淀系统的设计与实现

> **迁移自**：知识库治理的「知识缺口识别」模式 —— 重复提问 = 文档没写清楚的最强信号。

### 1. 一句话题目建议

**基于语义聚类与时序衰减加权的重复提问识别与 FAQ 自动沉淀系统的设计与实现**

### 2. 数据从哪来

**轨道 A（真实公开数据，算法验证用）：GH Archive**

已核实：http://www.gharchive.org/ —— GitHub 官方公开事件流，**15+ 种事件类型**（commits / forks / issues / comments 等），**按小时打包成 JSON.gz**，任意 HTTP client 可下载。这是完全免费、无需注册、无需 token 的真实数据源。

- 获取方式：`http://data.gharchive.org/2026-10-01-{0..23}.json.gz`
- 规模控制：只下载若干小时（每文件通常 100–300 MB），过滤 `type=="IssuesEvent"` 且 `payload.action=="opened"`，取 **3000–5000 条 issue 标题+正文**
- 数据列（字段）：issue 号、标题、正文、标签、仓库、时间戳、作者 —— 约 10 列，远低于 30 列红线

**轨道 B（自造中文 issue 集，系统演示 + 语义算法验证用）**：针对一个**虚构但合理的中文开源项目**（如「校园二手教材交易平台」）自造 2000 条 issue，字段：标题、正文、标签、提问者类型、是否已解答、重复 issue 编号。构造规则：按「问题类型 × 严重程度 × 环境配置」组合生成，并**人工注入 30% 的重复 issue**（同一问题不同人问、不同措辞）。

**为什么必须双轨**：GH Archive 是英文，bge-small-zh 是中文模型。论文里必须说清楚：英文轨道用 `all-MiniLM-L6-v2` 或 TF-IDF 基线做算法验证，中文轨道用 bge 验证语义向量的实际效果。**只跑英文不交中文，等于没做**；只跑中文自造数据，等于没有真实验证。两个都跑，答辩无死角。

**评委问「数据是真是假怎么答」**：

```python
# 算法三：重复判定与 FAQ 生成（你的核心改进点）
# 纯向量最近邻会把「相似但不同问题」误判为重复（如「怎么登录失败」vs「怎么注册失败」）
# 改进：语义相似度 + 关键词 Jaccard 相似度 + 标签一致性 三路加权
#   alpha * cosine_sim + beta * jaccard(tag) + gamma * jaccard(keyword)

```

# 5. 我明确不建议做的方向及理由

## 5.1 本文中已提出但不建议采纳的方案

### ❌ 3-B 基于 GNN 的跨文件缺陷传播预测（**最强烈不建议**）

| 理由 | 详情 |
|---|---|
| **违反 vibecoding 核心判据** | PyG + torch + CUDA 的版本兼容矩阵是公认的坑，在 Windows + 8GB 显存上安装失败率很高，且失败时的报错信息极难读懂。**这是一个「装不上就全盘皆输」的单点风险** |
| **需要调参才能收敛** | GCN 的 lr / hidden / epochs / dropout 必须调，训练不稳定时会出现「昨天 0.85 今天 0.62」，答辩时无法解释 |
| **图构建是 NLP 的活** | AST → 代码图需要 tree-sitter 或自写解析器，代码量与踩坑概率都远超软件方向 |
| **数据规模未能核实** | Big-Vul 的官方发布页与精确样本量本次未能核实，存在「论文里写的数字对不上」的风险 |
| **有「做不出来」的实质风险** | 13 个方案里唯一一个 |

**替代建议**：若你确实想做图算法方向，走 **3-C（社区发现）** 或 **2-B（权限图传递闭包）** —— 同样有图算法的含量与讲解空间，但**全是 NetworkX 无参调用，不需要 CUDA，不需要训练**。

### ⚠️ 3-D 引用网络影响力早期识别（**条件性不建议**）

- 技术上可行，**但与已占用的主题①（中文学术文献语义检索）领域相邻**。两个都做会显得你没有想清楚；查重系统也可能判定同源。
- **建议**：只在「你决定放弃主题①」时才考虑它。否则直接剔除。

### ⚠️ 4-C 多目标选址与资源分配（**优先级最低**）

- 技术难度是 13 个方案里最低的（5/5），但**与 4-A、4-B 的差异化太小** —— 三个都是「CP-SAT + 多目标权重 + 帕累托曲线」，评委看了 4-A 再看 4-C 会觉得重复。
- **建议**：如果不做 4-A 或 4-B，可以考虑；否则剔除。

### ⚠️ 1-C API 契约漂移检测（**有条件**）

- 差异化最好（14 题零命中），就业匹配度也高（**能直接写进测试开发简历**）。
- **但卡点集中在 Java 侧**（AST / 反射），4–6 天的卡住风险是 13 个方案里最高的。
- **建议**：**只有在你 Java 基础扎实、且导师认可「测试用例自动生成」这个落点时才选**。若 Java 较弱，直接剔除。

## 5.2 整体方向层面的建议

| 不建议方向 | 理由 |
|---|---|
| **任何需要 GPU 训练的方案** | 8GB 显存 + vibecoding = 双重不可行。3-B 就是典型反例 |
| **任何需要调参才能收敛的方案** | 与《校园场景选题方案.md》的核心判据直接冲突：调参失败时你无法在 10 分钟内定位问题 |
| **爬取中文论文全文（知网/万方）** | 前置文档已核实：服务协议限制 + PDF DRM。已有主题①②均已避开 |
| **RAG / Agent / Text2SQL 类** | 前置文档已核实：8GB 跑不动、Token 消耗高、Spider 2.0 榜单已被 Agent 占据、撞车率极高 |
| **通用商城 / 家政 / 宠物 / 点餐类推荐** | 往届 4 道重题（宠物商城、同城家政、海底捞点餐、非遗文化）已把这个模板占死 |
| **YOLO / 目标检测类** | 往届 2 道重题（玉米叶片病害、二手交易），且偏视觉非软件 |
| **需要真实企业账号/内网数据的方向** | 拿不到就等于做不成 |
| **算法含量低于「一个可评估模型 + 一处可消融改进」的方案** | 老师红线。2-B 的「最小冲突集」就是为满足这条而设计的 |
