## 0. 先承认问题：前面那五个方案确实太重了

你的质疑是对的。我复盘一下方案 A 和 B 的实际工作量：

| 方案 | 我列的隐藏工作量 | 单人 7 个月的现实判断 |
|---|---|---|
| A 交易欺诈 | 59万 × 460 列加载内存管理、目标编码防泄漏、460 列的特征分组设计、5 模型 × 3 策略 = 15 组实验、图特征构建、漂移监控 | ❌ 这是 2–3 人一学期的量，vibecoding 会崩 |
| B 销量预测 | 1115 条序列的时间窗交叉验证、促销/闭店日特殊处理、lag/rolling 特征组合调参、预测区间校准、安全库存公式推导 | ⚠️ 勉强，但卡在特征工程上会耗掉两个月 |

**更致命的是**：这两类数据集的「正确答案」在 Kaggle 上是公开的。你答辩时被问「你怎么知道你的特征设计是对的」，只能回答「Kaggle 高手说的」——这不是你的工作。

**校园选题恰好解决这个矛盾**：数据规模小到你能完全掌控，每个字段的来源和含义都能讲清楚，算法是真的但工程量小。这才是「本科毕设」该有的样子。

## 1. vibecoding 能做完 vs 做不完的分界线

这张表是你判断任何选题的工具，以后自己也能用：

| 维度 | 做不完（❌） | 能做完（✅） |
|---|---|---|
| 数据行数 | > 10 万 | < 5000 |
| 数据列数 | > 50 | < 30 |
| 数据来源 | 格式未知的 Kaggle 竞赛数据 | 自己构造，字段含义明确 |
| 算法 | 需要调参才能收敛的深度模型 | 有现成库封装、参数默认值就能跑 |
| 依赖 | 显存 / 集群 / 特殊 CUDA 版本 | `pip install` 后 import 就能用 |
| 状态管理 | 分布式 / 消息队列 | 单体应用 + 数据库 |
| 出 bug 时 | 不知道是算法错还是环境错 | 打印中间结果就能定位 |

**核心判据**：**当一个 bug 出现时，你能不能在 10 分钟内定位它**。59 万行数据跑 LightGBM 结果不对，你无从下手；50 行数据跑图着色结果不对，画出图看一眼就知道哪两个节点冲突了。

## 2. 校园选题的真正难点：别做成"管理系统"

老师的红线里，「基于 SpringBoot 的 XX 管理系统」被明确点名。校园选题天然容易掉进这个坑——「学生管理系统」「选课系统」满大街都是。

**破解思路：把算法放在"冲突"上，而不是放在"数据"上。**

校园里有一个真实的、到处都存在、但几乎没人做好的问题：**资源冲突消解**。

- 同一个教室，两门课都排到周三第 3-4 节 → 冲突
- 同一个学生，数据结构和高数都选，且都考周一 → 冲突
- 同一台设备，两个实验室都预约了周四上午 → 冲突
- 同一个教师，同时带两个班的实验课 → 冲突

这是一个**数学上明确的问题**（约束满足 / 图着色），不是"数据管理"问题。而且：

- **数据自造且合理**：一门课有多少个班、几个时段、几个教室 —— 全是你可控的规则
- **算法是真的**：图着色 + 贪心 + CP-SAT 约束规划，都是正经算法
- **有现成库兜底**：OR-Tools 是 Google 开源的约束求解器，Python / Java / C# 都有绑定，**默认参数就能出解**
- **结果可视化极强**：课程表热力图、冲突消解前后对比，截图撑论文
- **你比任何人都懂这个场景**：答辩时你能说出「我们学校真实的痛点是……」

## 3. ★ 首选方案：基于约束求解的教室资源冲突消解与排课优化系统的设计与实现

### 3.1 问题定义（写进论文就是问题建模章节）

**输入**：
- 课程表：课程名、授课班级、选课人数、每周课时数
- 教师表：姓名、可用时段、不可用时段
- 教室表：编号、容量、设备类型（多媒体/机房/普通）
- 时间槽：每周 5 天 × 每天 6 节（大班课/小班课可分开处理）

**约束（硬约束，必须满足）**：

1. 同一教室同一时间只能被一门课占用
2. 同一教师同一时间只能上一门课
3. 同一班级同一时间只能上一门课
4. 教室容量 ≥ 选课人数
5. 需要机房的课程只能安排在机房

**优化目标（软约束，最大化满足）**：

1. 减少教室闲置（把选课人数接近教室容量的课排在同一教学楼）
2. 避免连续多节课排给同一教师
3. 避免学生连续跨校区移动（同一栋楼尽量连排）
4. 满足教师的时间偏好（软约束）

### 3.2 算法（三层递进，构成论文第 2、5 章的主体）

```python
# 第 1 层：基线 —— 贪心图着色（NetworkX，一行代码）
import networkx as nx
coloring = nx.coloring.greedy_color(G, strategy="largest_first")
# NetworkX 官方提供 greedy_color，支持 largest_first / DSATUR 等策略
```

```python
# 第 2 层：CP-SAT 精确求解（Google OR-Tools，约束直接翻译成代码）
from ortools.sat.python import cp_model
model = cp_model.CpModel()
# 变量：assignment[course_id, room_id, slot_id] 是布尔变量
# 约束：每门课的每个时段恰好分配一个教室
# OR-Tools 官方返回 OPTIMAL / FEASIBLE / INFEASIBLE 三种状态
```

**第 3 层（论文的创新点）**：在 CP-SAT 目标函数里加入软约束权重

```python
# 目标函数：最小化 Σ w_i × violation_i
# 例如：同一教师连排两节 → 权重 1
#       跨校区移动      → 权重 3
# 通过调整权重 w_i，观察解的质量变化，画出帕累托前沿
```

**这一层是你能写出"改进"的地方** —— 不是改算法本身，而是设计约束权重体系并做参数分析。这是本科生完全做得出来的算法工作，答辩时讲得清楚，且能画出很多图。

### 3.3 为什么 vibecoding 能兜住

| 环节 | 复杂度 | 说明 |
|---|---|---|
| 数据构造 | ⭐ | 写个 Python 脚本按规则生成 200 个课程、30 个教室、60 个教师 —— 半天 |
| 建模 | ⭐⭐ | 贪心着色一行代码；CP-SAT 官方有 scheduling 教程和完整示例（课程排程本身就是官方示例场景） |
| 求解 | ⭐ | OR-Tools 默认参数直接出解，设置 `max_time_in_seconds = 30` 就能保证不卡死 |
| 调优 | ⭐⭐⭐ | 唯一需要动脑的地方，也是论文唯一的算法贡献点 |
| 前端 | ⭐⭐ | 课程表用 ECharts heatmap 或简单的 HTML table，都有一堆开源模板 |
| 后端 | ⭐⭐ | Spring Boot / FastAPI CRUD，vibecoding 强项 |

**最大的风险点只有一个**：约束建模写得对不对。但这个可以 10 分钟验证 —— 排 10 门课，手工检查有没有冲突，立刻知道。

### 3.4 系统模块（8 个，够撑工作量也够撑论文）

1. **基础数据管理**：课程、教师、教室、学生班的增删改查与导入导出
2. **排课规则配置**：硬约束开关、软约束权重配置界面
3. **冲突检测模块**：对已有课表实时检测所有冲突类型，输出冲突清单
4. **自动排课模块**：调用算法求解，生成课表
5. **课表可视化模块**：周视图课程表、教师个人课表、教室占用热力图
6. **人工调整模块**：支持拖拽调课，每次调整后实时重新检测冲突
7. **方案对比模块**：同一批约束下，贪心解 vs CP-SAT 解的差异对比（**论文实验章节的核心**）
8. **导出模块**：导出 Excel / PDF 课表

**数据库设计（9 张表，ER 图有真实内容）**：课程表、教师表、教室表、班级表、课表表、排课任务表、约束配置表、调整记录表、用户表。

关系很自然：`课程` N 对 N `教师`（授课），`班级` N 对 N `课程`（选课），`课表` 是 `课程 × 时段 → 教室` 的三元关联 —— 这个三元结构画在 ER 图里非常清楚。

### 3.6 开源资源（全部是大厂标准件，不是冷门技术）

| 用途 | 资源 | 热度 |

### 3.7 差异化（防查重）

往届 14 个题目里，0 个涉及排课算法。你能做的差异化：

1. **题目写"约束求解"而非"管理系统"** —— 一眼就和"教务管理系统"区分开
2. **软约束权重体系** 是你的算法贡献点，可以展开成一整章
3. **数据是你们学校真实的课程/教师/教室规模**（比如「基于 N 个班级、M 间教室的真实排课场景」），具体数字写进题目，别人抄不走

### 3.8 唯一真实风险

**你拿不到学校真实的排课数据**（涉及隐私和权限）。

**对策**：完全公开说明「数据根据 XX 学院的公开培养方案与教室资产规模模拟生成」，并把生成脚本放进附录。这在毕设里是完全可接受的 —— 排课问题本身是公开研究问题，重点是算法和系统，不是数据的真实性。

## 4. 备选方案：基于先修关系图谱的个性化学习路径规划系统的设计与实现

### 4.1 问题定义

计算机专业培养方案里，课程之间有**先修关系**：学完《程序设计基础》才能学《数据结构》，学完《数据结构》才能学《算法设计》...

**问题**：学生已经学过（或正在学）某些课，选修后续课时，如何推荐一条**路径最短、难度适配、时间可行**的学习路线？

### 4.2 算法（三层，同样是白送的对比实验）

```python
# 第 1 层：先修关系建图 + 拓扑排序（判断选课是否合法、课程顺序是否可达）
# 课程 = 节点，先修关系 = 有向边，构成 DAG

# 第 2 层：学习路径规划 = DAG 上的最短路径 / 拓扑序选择
# 目标：找到包含所有目标课程的最短学习路径
# 这是经典图论问题，有教科书级别的算法

# 第 3 层：个性化加权（你的贡献点）
# 根据学生的已修课程、成绩、时间预算、课程难度评分，
# 构造带权图，用 Dijkstra / 贪心求最优路径
```

数据极小：**一门专业 40–60 门课**，手工整理培养方案 + 先修关系，一两天就能录完。这比 59 万行 CSV 好处理一百倍。

### 4.3 差异化亮点

「基于知识图谱的学习路径推荐」在文献里不算新（智慧树等平台已有），但你的差异化是：

1. **不做 NLP 抽取**（文献里那些用 BERT/CRF 抽先修关系的，那是 NLP 方向，不适合你）
2. **先修关系手工录入** —— 规模小，没必要上机器学习抽取，答辩时反而说「因为规模有限，人工整理更准确」
3. **重点放在路径规划的图算法与个性化加权**，这是运筹/图论味道，评委会觉得扎实

### 4.4 系统模块（7 个）

1. 课程与先修关系图谱管理（节点/边增删改查 + 图可视化）
2. 学习者档案管理（已修课程、成绩、时间预算、目标课程）
3. 选课合法性校验（拓扑序检查，自动指出未满足的先修课）
4. 路径规划求解（调用图算法，返回推荐路径）
5. **知识图谱可视化**（DAG 图形化展示，高亮推荐路径 —— 截图效果极佳）
6. 学习计划制定与进度跟踪
7. 图谱数据导入导出

**数据库**：课程表、先修关系表、知识点关联表、学生档案表、学习计划表、进度记录表、用户表。ER 图里课程-先修关系是个漂亮的多对多自关联。

### 4.5 风险

- **算法含量偏低**：图论算法是「老算法」，评委可能觉得不够新。应对：在论文里补充算法复杂度分析与不同策略的实验对比（拓扑排序 vs BFS 层序 vs Dijkstra 加权）
- **系统可视化要求高**：图谱可视化如果做得简陋，观感差。用 ECharts graph 或 AntV G6，都有现成模板

## 5. 第三备选：基于多源行为数据的学业风险预警系统的设计与实现

> **难度评级：数据获取是唯一的坎，算法本身最简单**

### 5.1 数据来源（两条路，推荐第二条）

| 路径 | 做法 | 问题 |
|---|---|---|
| 路径 A | 用 UCI 的 Student Performance 数据集（葡萄牙学生，33 个特征） | 字段是葡语/英文，与国内课程体系对不上，答辩时无法解释「这个特征对应我们学校的什么」 |
| **路径 B（推荐）** | **自己构造 + 用公开数据集做算法验证双轨并行** | 数据是造的，需要在论文里说清楚 |

路径 B 的做法：构造一个 3000 条规模的合成数据集（4 个年级 × 每年级若干人 × 若干学期），字段包括：出勤率、作业提交率、期末成绩、图书馆借阅次数、竞赛参与、绩点、已获学分……按合理规则生成标签（是否挂科、是否退学预警）。

**同时**用 UCI Student Performance 数据集验证你的特征工程管线有效 —— 这样论文里既有「我的数据」，又有「我的方法在公开基准上也被验证了」。

### 5.2 算法（最简单，工作量最轻）

```python
# LightGBM 二分类，参数用默认值就能跑
# 关键不在模型，在于「特征工程」和「阈值策略」
# 阈值策略 = 业务逻辑：漏报一个危险学生 vs 误报一个好学生，哪个代价更大？
```

**真正的算法工作**在于**分层预警**：不是简单的「是/否」，而是「正常 / 关注 / 预警 / 高危」四级，每级用不同的阈值。这个设计在答辩时很有说服力 ——「不是说预测挂科，而是建立一个四级干预流程」。

### 5.3 为什么这个可能是最稳的

- **算法门槛最低**：LightGBM 默认参数就是最好的参数，不用调
- **系统工作量大**：数据看板、预警列表、干预记录、辅导员工作流、通知推送 —— 7–8 个模块，vibecoding 的舒适区
- **答辩好讲**：「我做了一个学业预警系统，用 LightGBM 预测学生挂科风险，SHAP 解释出主要风险因子是出勤率和作业提交率，系统给辅导员生成了干预名单」
- **SHAP 可选加**：加了就多 3–4 页图表，不加也不影响成立

### 5.4 致命风险

**数据是自己造的**。评委一定会问：「你这个数据是真的吗？」

**必须准备的答案**（写进论文，不是临场编）：
1. 数据构造规则参照真实教务系统的字段设计（可以说参考了本校教务系统的表结构）
2. 分布合理性验证：对生成数据做分布对比图，与公开数据集 Student Performance 的特征分布对照
3. 算法泛化性验证：在 UCI 真实数据集上跑同一套管线，报告结果，证明方法不是只在合成数据上有效

**如果答辩老师追问很凶**，就换回方案一或方案二 —— 那种题目没有「数据真假」这个问题。

| **延毕风险** | **低** | 低 | 中 |
| **推荐度** | **★★★★★** | ★★★★ | ★★★ |

### 我的建议

**选方案一（排课冲突消解）**。理由：

1. **唯一没有"数据真假"软肋的方案** —— 排课问题本来就是公开研究问题，你构造数据完全站得住
2. **算法是真的且有层次** —— 贪心 → CP-SAT → 加权优化，三层递进，论文写不满都难
3. **约束求解（OR-Tools）是 Google 开源、有官方课程排程示例**，vibecoding 完全兜得住
4. **场景极其贴合校园** —— 答辩时你可以真的说出「我们学校 XX 学院有 X 个班、X 间教室，排课是真实的痛点」
5. **有可视化冲击力** —— 课程表热力图和冲突消解动画，是答辩演示最好的素材

## 7. 校园选题的额外优势：答辩现场能演

前面几个方案（欺诈检测、销量预测）答辩时只能展示网页和数字。**校园选题能演一个"过程"**：

- 打开一个冲突的课表 → 系统红色高亮标出 3 处冲突
- 点「自动重排」→ 3 秒后课表刷新，冲突清零
- 打开「方案对比」→ 贪心解和 CP-SAT 解并排显示，冲突数分别是 7 和 2

这个演示的说服力，比任何 PPT 都强。而且**录屏存档**（西南交大等校要求提交演示录屏）也天然有内容。

## 8. 落地纪律（针对 vibecoding 特别定制）

1. **第 1 个月末必须交付**：数据构造脚本 + 贪心算法跑出第一张课表。这是最小可验证闭环。
2. **数据规模从小的开始**：先 20 门课 3 间教室跑通，再扩大到 200 门课。OR-Tools 求解时间随规模增长，控制不好会卡死。
3. **求解器必须设超时**：`solver.parameters.max_time_in_seconds = 30`。这是防止演示当天卡死的保险丝。
4. **每周末提交一次可运行的版本**。不要攒到最后。vibecoding 的代码债是指数增长的。
5. **论文与系统同步写**。每完成一个模块立刻写对应章节 + 截图。系统做完再写论文必然写不满 70 页。

## 9. 下一步（建议本周内完成）

**只有一件事是真正紧急的**：先跑通最小闭环。

```
下午 3 小时可完成：
1. 用 Python 写 50 行脚本，生成 30 门课 / 5 间教室 / 4 个班的测试数据
2. 用 NetworkX greedy_color 排出一版课表，打印出来
3. 手工检查有没有冲突（这是验证建模正确性，不是验证算法优劣）
4. 跑通后，把数据规模放大到 200 门课，设 30 秒超时，看 OR-Tools 能出什么
```

如果第 4 步能出解，**这个选题就成立**，剩下的都是时间问题。如果第 4 步跑很久或无解，说明约束建模要简化，也就提前知道了。

跑完拿结果去见导师，附一句：「我打算做这个，已经有第一版结果了，X 秒排出 X 门课、0 冲突。」
