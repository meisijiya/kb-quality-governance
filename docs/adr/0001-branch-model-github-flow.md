# ADR-0001：分支模型采用 GitHub Flow 精简版

- **状态**：已采纳
- **日期**：2026-10-19
- **决策者**：项目作者（单人开发）
- **相关**：[`AGENTS.md`](../../AGENTS.md) 分支管理规范

## 背景

项目需要一个分支模型来支撑 17 周（2026-10-14 → 2027-02-09）的开发排期。初稿设想是「主分支 + feature 分支 + fix 分支」三类分支。落地前先做了公开调研（Git Flow / GitHub Flow / Trunk-Based Development 的适用场景、分支寿命、合并冲突成本、分支命名惯例），再定模型。

## 调研结论

| 策略 | 复杂度 | 分支寿命 | 适用场景 | 代价 |
|---|---|---|---|---|
| Git Flow | 高 | 天 ~ 周 | 版本化发布、多版本并行维护 | 长期分支发散、合并冲突频繁、拖慢交付速度 |
| GitHub Flow | 低 | 小时 ~ 天 | Web / 服务型高频部署 | 无显式发布管理 |
| Trunk-Based Development | 低 | 小时 | DORA 认定的高绩效团队 | 依赖强 CI/CD 与特性开关 |

三种策略的共同前提是**团队规模、发布节奏、部署策略**三者之一与模型匹配。本项目的实际约束是：单人开发、无生产部署、不维护多版本并行发布、交付物是论文与可演示系统而非对外发版服务。

## 决策

采用 **GitHub Flow 精简版**：

- `main` —— 唯一长期分支，始终可交付，受分支保护规则约束
- `feature/<slug>` —— 从 `main` 切出的短期功能分支
- `fix/<slug>` —— 从 `main` 切出的短期缺陷修复分支
- 里程碑以 `main` 上的 annotated tag 记录，**不设 `release/*` 分支**

## 理由

1. **不引入 `develop` 集成分支。** Git Flow 最大的两个坑是「长期分支显著发散」与「合并冲突频繁」。单人项目只有一个开发者，同时维护 `main` 与 `develop` 两条长期分支，换来的集成收益为零，发散成本却是实打实的。
2. **不引入 `release/*` 分支。** Git Flow 的 `release/*` 服务于「显式版本化发布 + 多版本并行维护」。本项目不对外发版，也不需要同时维护多个线上版本。里程碑用 `main` 上的 tag 记录，拿到同样的可追溯性，不承担分支同步成本。
3. **保留 `fix/*` 而不设 `hotfix/*`。** `hotfix/*` 的语义前提是有线上生产环境需要紧急绕过发布流程。本项目无生产环境，紧急修复直接走 `fix/*` 即可。
4. **不采用 Trunk-Based。** 该模型要求强 CI/CD 与特性开关作为兜底。本项目当前没有 CI 流水线，直接推 `main` 会让 `main` 失去「始终可交付」这一性质，收益（交付速度）不足以补偿风险（失去门禁）。

## 单人开发下的分支保护取舍

调研中关于单人项目的明确结论是：保留「必须走 PR 才能合并」与「状态检查必须通过」，但**跳过「需要审核批准」**（自己无法批准自己的 PR，开启会导致 PR 永远无法合并），并关闭「过期批准作废」与「需要 Code Owner 审核」。

本项目当前没有 CI 流水线，因此**暂不要求状态检查**（无状态检查可要求时勾选此项会导致所有 PR 卡死）。待 CI 落地后再启用该规则，此处同步更新。

## 后果

- **正面**：只有一条长期分支，合并冲突面最小；`main` 保持随时可交付；里程碑可追溯。
- **代价**：没有 `release/*` 分支，意味着「发布前的版本冻结」这一动作需要在 `main` 上用 tag 直接承担，没有独立的分支空间做灰度准备。对本项目而言这是可接受的——没有灰度需求。
- **待办**：CI 流水线落地后，在 `main` 的分支保护规则中启用「Require status checks to pass before merging」。
